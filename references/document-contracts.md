# 文档交付契约

这些结构是完整性检查表，不是必须照抄的固定目录。优先沿用项目已有文档和术语。

## 产品需求文档

一份可实施的产品需求至少能回答：

- 目标用户、问题、目标结果和非目标；
- 角色、权限和可见范围；
- 主流程、替代流程和异常流程；
- 业务规则、状态转换、时间条件和限制；
- 页面、入口、字段、动作及反馈；
- 数据结果、通知、审计和外部依赖；
- 明确的验收标准；
- 已知缺口、待决策项和发布边界。

复杂行为应分配稳定需求标识。不要把接口路径、表字段清单或测试执行记录直接堆进产品目标章节。

如果只能从代码确认当前行为，无法确认目标用户、目标结果、非目标或产品决策，则只能交付“当前实现说明”，不能把它命名为已确认 PRD，也不能通过 `product_requirements` 的最终门禁。

## 测试用例

每个测试用例至少包含：

- 用例标识和关联需求；
- 测试目的与优先级；
- 前置状态、角色、权限和数据准备；
- 可重复执行的步骤；
- 每个关键步骤的预期结果；
- 数据、状态、通知或审计结果；
- 自动化、人工或外部验证方式；
- 当前覆盖状态和最近证据。

测试集应按适用范围覆盖：

- 正常路径和最小输入；
- 边界值、空值、重复提交和非法输入；
- 权限不足、资源不存在和状态不允许；
- 部分成功、超时、结果未知、重试和恢复；
- 并发、事务、幂等和重复事件；
- 历史数据、升级兼容和回滚；
- 页面 loading、空态、错误态和禁用态；
- API、任务、事件、通知和外部依赖失败；
- 安全、隐私和敏感信息可见性。

“检查功能正常”不是可执行用例。

测试文档完整表示范围内规则已经转成可执行用例并说明当前覆盖状态，不表示所有用例均已自动化。缺少运行环境时必须区分“用例已编写”和“本批次已执行通过”。

## 数据字典

每个真实实体或表应记录：

- 业务含义和数据所有者；
- 主键及重要关联；
- 字段名、显示名、类型、长度和是否可空；
- 默认值、枚举、约束和校验；
- 值来源、写入入口和更新时机；
- 敏感性、可见范围和保留策略；
- 索引、唯一性和关键业务不变量；
- 历史兼容或迁移说明。

以当前 schema 或等价事实为准。模型属性、接口字段和界面标签不能单独证明数据库字段存在。

没有持久化层的项目可以将数据维度标记为不适用，但仍需说明输入、输出、事件或临时状态；不能因为没有传统数据库就跳过数据责任。

## 用户或运营手册

按使用目标组织，而不是按代码模块组织。每个场景至少说明：

- 谁在什么前提下使用；
- 从哪里进入；
- 页面上需要识别的关键信息；
- 按真实顺序执行的操作；
- 成功后会发生什么；
- 常见失败、禁止条件和处理办法；
- 需要转交给谁或进入哪个后续流程；
- 对应版本和适用角色。

手册只描述用户能观察到或必须理解的技术边界。不要暴露密钥、内部地址、真实客户数据或无需公开的实现细节。

无法运行界面时，手册只能标注为基于静态实现核对；按钮文案、权限态、空态和错误反馈未经运行验证时不能声称 `VERIFIED`。

## 文档之间的一致性

- PRD 定义的状态必须能在数据、界面或接口事实中找到落点；
- 测试用例必须覆盖 PRD 的验收标准和关键异常；
- 数据字典的字段、枚举和关系必须与当前 schema 一致；
- 手册的入口、按钮、字段和结果必须与真实系统一致；
- 任何一份文档标注的未实现能力，不能在另一份文档中写成已上线。
